# M7 模型封装与可复现交付口径

## 1. 目的与边界

M7 将已经通过 M0～M6 验收的 CDU Mini Loop 封装成稳定、可安装、可追溯的独立仿真组件。
本阶段只统一既有 M2 稳态、M3 开环动态、M4 PI 闭环和 M6 验证场景，不新增优化器、
策略库、代理模型、智能体、DCS/SIS/LIMS 接口或现场控制能力。

M7 交付仍是低可信工程仿真工具。安装成功、结果可复现和保护场景通过均不代表现场动态精度、
真实液位、阀门行程、仪表故障诊断或安全完整性等级已经验证。

## 2. 统一运行类型与状态

稳定入口只接受四种运行类型：

- `steady_recycle`：调用 M2 物理循环稳态求解；
- `open_loop_dynamic`：调用 M3 开环动态场景；
- `closed_loop_dynamic`：调用 M4 七回路闭环场景；
- `validation_scenario`：调用版本化 M6 场景或结构拒绝入口。

公共状态固定为：

- `success`：数值执行和该层验收均通过；
- `limited`：结果在版本化受限/代理适用域内有效；
- `rejected`：输入在求解前被结构性拒绝；
- `not_converged`：稳态或数值迭代未收敛；
- `failed`：执行、守恒、结果契约、写出或重载失败。

公共状态不能覆盖底层状态；运行结果同时保存 `engine_status`、失败阶段、失败原因和最后有效证据。

## 3. 运行输入与包内资源

稳定 API 只接受严格、不可变、可序列化的 `RunRequest`，拒绝未知字段、布尔数值、非法枚举、
路径穿越和与运行类型不兼容的字段。预设由固定 ID 注册表加载，不扫描任意目录。

wheel 必须通过 `importlib.resources` 提供以下 11 项只读资源：

- 基础模型、六伪组分目录和基础案例；
- M3 开环基准/+5%进料场景；
- M4 控制器、闭环基准/+5%进料场景；
- M6 验证配置和正式套件 manifest；
- M5 运行覆盖层。

M5 正式参数 JSON 是审计产物，不是 `ModelConfig`。默认运行按“基础模型/案例 + 严格白名单覆盖”
构造有效输入：模型侧只覆盖洗水比和两个切割点，案例侧只覆盖闪蒸温度；覆盖层必须引用 M5
manifest、参数产物和结果指纹，并保留 `case_alignment_only` 声明。基础文件不得原地修改。

每次发布运行必须按固定顺序带齐这 11 项资源；资源字节、输入 artifact SHA-256 和
`source_fingerprints` 必须与已安装包内副本交叉一致。包内资源与仓库版本化源文件还必须有
逐字节 SHA-256 一致性测试。规范化对象字典不能在没有专用 loader 的情况下冒充原始
JSON 输入。

在固定预设之上，M2/M3/M4可接受版本化受控自定义层；该层只能通过公开输入ID修改进料/工况、
两切割点、动态参数、三个质量库存初值和版本化动态事件。输入目录必须冻结显示单位、SI转换、范围、
适用运行类型和目标路径；未知键、错放分区、不闭合组成、非法动态网格或事件必须在求解前拒绝。
M6便携预设保持冻结，不接受该层。旧运行目录的`inputs/`仍是只读证据，不能作为修改入口。

用户请求文件采用严格稀疏覆盖：只强制`preset_id`，未写合同字段、工况、初态和场景部分全部继承
固定preset；写入运行目录前必须先合并为完整`RunRequest`。未知字段、保留元数据覆盖及显式版本或
运行类型漂移仍在求解前拒绝，稀疏入口不能降低正式请求与artifact合同强度。

自定义运行继续以预览指纹确认：`preview(request)`先在不调用M2/M3/M4求解器的情况下构造有效
模型、案例、场景、动态初态和指纹；`run()`只有收到完全匹配的预览指纹才执行。普通CLI的
`run --request`在同一命令中展示预览并询问，人工确认后自动传回该指纹；非交互CLI和Python API使用
显式指纹。预览后任何请求变化都会使旧确认失效。显示选项不进入物理结果指纹，但解析后的有效输入
必须进入来源和执行输入指纹。

## 4. 稳定 Python 与命令行入口

Python 外观冻结为：

```python
request = load_preset("closed-loop-feed-step")
outcome = run(request, output_root=Path("runs"))
record = read_run(outcome.run_dir)
```

自定义请求先调用`resolved = preview(request)`，再将
`resolved.preview_fingerprint`作为`expected_preview_fingerprint`传给`run()`。

命令行提供：

- `cdu-mini presets`；
- `cdu-mini inputs --preset <id> [--json]`；
- `cdu-mini template --preset <id> [--output <request.json>]`；
- `cdu-mini preview --preset <id>|--request <request.json> [--json]`；
- `cdu-mini run --preset <id> --output <dir>`；
- `cdu-mini run --request <request.json> --output <dir>`（同命令预览并交互确认）；
- `cdu-mini run --request <request.json> --confirm-preview <fingerprint> --output <dir>`；
- `cdu-mini batch --request <batch.json> --output <dir>`；
- `cdu-mini batch --resume <batch-dir>`；
- `cdu-mini inspect <run-dir> [--json]`。

同时支持 `python -m petroleum_rto.cdu.runtime`。CLI 只负责解析和显示，物理执行必须走同一个
Python API，不能维护第二套模型逻辑。

普通`run`和`inspect`从严格重载结果中生成分层关键摘要：M2产品/收率/性质/能量，M3/M4温压、
三库存、产品、事件和守恒，M4再增加七回路误差/输出/饱和/稳定时间。`--quiet`只保留一行，
`--verbose`追加版本指纹，`--json`返回同一摘要的结构化表示；普通成功输出不重复模型卡全文。

## 5. 运行目录与提交语义

每次执行创建唯一、不可覆盖的 `runs/<run_id>/`，至少包含：

- `request.json`：严格运行请求；
- `inputs/`：固定 11 项、与已安装包逐字节一致的原始资源副本；
- `result.json`：公共状态、摘要、版本、来源和指纹；
- `timeseries.jsonl`：动态样本，逐行写出；
- `events.jsonl`：配置、保护和失败事件；
- `error.json`：失败时的结构化错误；
- `manifest.json`：最后发布的完成标志。

所有文件先写到同目录临时文件，重读、解析、大小和 SHA-256 校验后再发布；`manifest.json` 必须
最后发布。无 manifest 的目录是 `incomplete`，reader 必须拒绝将其当作有效运行；出现未发布的
`.stage`/`.tmp` 文件或合同外的孤立文件时也必须拒绝。已有运行目录不得覆盖；失败结果也必须
保留，且不能覆盖先前成功结果。

动态轨迹按 JSONL 逐样本写出并边写边计算文件 SHA-256。完整结果指纹在保持与规范 JSON
完全相同的前提下逐样本增量计算，不用一次 `as_dict()` 展开整条轨迹后再复制第二份大对象。
`read_run()` 以一次顺序 JSONL 读取适配器把样本交给结果合同，避免先 `read_text().splitlines()` 构造一份
原始轨迹副本；重建后的 `ExecutionPayload` 本身仍保留一份完整轨迹。

## 6. 运行清单与可追溯性

`run_id` 只保证目录唯一；确定性复现键是请求、有效输入和结果指纹。manifest 至少记录：

- 软件分发版本和已安装源码树 SHA-256；
- Git commit/dirty（只作辅助；不可发现时字段仍必须存在并写为 `unavailable`）；
- 模型、基础参数、M5 覆盖（`m5_overlay_version`）、案例、控制器、场景和 M6 配置版本；
- 每个输入资源的原始 SHA-256、规范对象指纹和有效输入总指纹；
- 随机种子及是否实际使用随机性；
- Python 完整版本、实现、操作系统、架构和分发包版本；
- UTC 开始/结束时间和耗时；
- 每个产物的路径、字节数、SHA-256、schema 和媒体类型；
- 公共状态 `runtime_status`、底层状态 `engine_status` 和适用域状态 `domain_status`；
- 与结果完全一致的 `source_fingerprints`、来源、合成标志和声明范围。

当前 M4～M7 可能未提交，因此只记录 Git SHA 不足以证明运行代码；已安装源码树 SHA-256 是强制项。
时间、`run_id`、输出目录和显示选项不得进入物理请求或结果的确定性指纹。

## 7. 批处理与恢复

批请求冻结有序 item 和批请求指纹。执行按顺序进行，单项失败不终止后续项。批目录保存追加式
事件和最终 batch manifest。公共 `read_batch()` 严格核对批请求、事件、最终清单、每个 item 的
run manifest、顺序、attempt 路径及所有指纹。恢复时必须先核对原批请求指纹：

- manifest 和文件哈希有效的完成项直接跳过；
- 无 manifest 的不完整项新建 attempt 重跑；
- 已失败项默认保留，只有显式 `retry_failed` 才创建新 attempt；
- 任何恢复或重试都不得覆盖旧成功或失败证据。

已完成批次再次恢复时，必须先把当前 `batch_manifest.json` 按其内容指纹原子地移入
`history/manifest-<fingerprint>.json`，再追加 `batch_resumed` 事件。因此恢复中再次中断时，当前批次保持
明确的未完成状态，旧清单仍是可校验的不可变历史；下一次 `resume_batch()` 可在不覆盖证据的情况下
继续。

## 8. 来源、模型卡与禁止用途

模型卡必须披露：六伪组分与大多数设备参数是低可信工程初值；M5 只对单案例的两个切割点做
alignment；无现场动态验证；M4“液位”是库存代理；M6 保护不是 SIS；不确定区间是固定 Jacobian
工程包络而非统计置信区间。

禁止把本包用于现场闭环控制、SIS 设计/验证、安全完整性证明、产品质量保证、操作许可、在线优化
或绕过现有联锁。现场观测、M2/M3/M4/M6 合成结果和 M5 混合来源必须分节标识。

## 9. 性能基线

正式性能记录至少覆盖 M2 基准、M3 2 h +5%进料、M4 2 h +5%设定值和一个 M6 异常场景。
每项记录样本数、数值步长、wall time、Python 分配峰值和环境指纹；重复三次，报告中位数和最大值。
跨机器性能只报告，不设脱离环境的过紧硬阈值。

## 10. 发布门禁

M7 完成必须同时满足：

1. 全部 pytest、ruff、strict mypy 和 `pip check` 通过；
2. 请求、结果、事件、错误、manifest、tamper 和 path traversal 反例通过；
3. M2 基准、M3 +5%、M4 +5%和选定 M6 异常从统一入口完整复现；
4. manifest-last、失败隔离、reader 篡改拒绝和批恢复通过；
5. 包内资源与仓库源文件 SHA 一致，默认 M5 覆盖白名单完整；
6. 构建 wheel，在仓库外新建 Python 3.12 干净环境安装；
7. 干净环境执行 `cdu-mini run --preset steady-baseline` 并由 `read_run` 成功读取；
8. 模型卡、数据字典、使用说明、性能基线和发布清单与代码/产物一致。

只有 manifest 有效、统一入口可复现、wheel 干净环境验收通过且 M0～M6 回归不退化时，M7 才能
标记完成。
